# TEops (Thomson Projects): Build Spec

Last verified against code: 17 Oct 2026

Internal operations app for Thomson Energy Australia (electrical and solar contractor). Live at projects.thomsonenergy.com.au, with thomsonprojects.netlify.app kept as a working backup. The code is the source of truth: if this file and the code disagree, fix this file.

**Stack:** Netlify (Git-connected deploys, serverless and scheduled functions) · Supabase (Postgres, auth, storage) · Xero (Accounting API + Payroll AU API, **live**, real company) · Anthropic API (AI extraction, generation, assistant) · AssemblyAI (meeting transcription) · Airwallex (client payment links) · Gmail API (shared sales@ inbox, **live**) · Web Push (phone notifications, **live**) · Pylon (solar design, pull and push) · Formbay (STCs, webhook receiver only so far) · ABR (ABN lookup).

**Credentials:** integration keys live in the Supabase `api_keys` table, edited in Settings > API Keys, and are read server-side with `getIntegrationKey()` (`netlify/functions/_shared/get-integration-key.js`; it falls back to a `<NAME>_API_KEY` env var only if no row exists). Keys in use: anthropic, assemblyai, abr_guid, airwallex_client_id / api_key / webhook_secret, xero_client_id / client_secret / webhook_key, google_client_id / client_secret / refresh_token, pylon, formbay, formbay_webhook_secret, vapid_public_key / private_key, servicem8 (import only). Only platform secrets stay as Netlify env vars: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DEV_MODE_PASSWORD`, `GITHUB_TOKEN` (bugs sync), `CLAUDE_AGENT_KEY` (agent comments), `PDF_KEEP_BROWSER` (optional).

**Deployment:** edit in the local GitHub clone, commit and push, Netlify auto-deploys. **Run Supabase migrations before or alongside the deploy.** Bump the `?v=` on any edited JS/CSS (10 minute cache). Latest migration: 155 in the old `docs/archive/old-migrations/` numbering; new ones live in `supabase/migrations/` (latest 20261018120000).

**Ordering:** Roadmap and Part 0 (priorities) first, Part A is everything live, later parts are what is still missing.

## PART 0: Go-live priorities

**Aim: the whole company working in the app from day one.** Anything not on the day-one list must not block starting.

8. **ServiceM8 cutover:** re-run the SM8 import (Settings > ServiceM8 Import) on cutover day, then the attachment copy.

## PART A: Built and live

### A1. Time tracking and payroll
- Clock in / clock out overlays appear on the tap with Loading..., and show an error card with Close if the load fails (UX 1). A job with one stage is preselected on My Day (UX 6). Break start defaults to 12:00 (or mid shift) when a break is asked (UX 16). Home has a Switch job button (UX 7). Timesheets has a This week button (UX 18).
- Clock in/out against job and stage from My Day; manual entries; leave requests, approved or declined by Admin or Finance on Timesheets (24 Oct 2026, was Admin only); staff scheduling calendar.
- **Leave balances (24 Oct 2026, migration 20261124150000):** `public.leave_balances` holds each person's annual, sick and long service hours copied from Xero Payroll (`sync-leave-balances.js`, every night; `sync-leave-balances-now.js` behind **Refresh from Xero** for Admin and Finance, and run again by the Timesheets page after every Xero timesheet push, 26 Oct 2026). Staff see their own on the Staff page and above My leave requests on Timesheets; Admin and Finance see everyone's, and each person's on the Leave card. Xero stays the source of truth; the app never writes leave to Xero.
- **My Day task cards** (Your scheduled tasks, Free tasks up for grabs): main tasks only (subtasks counted as "3 of 5 subtasks done", not listed; a subtask of yours still shows when its main task is not yours), split Prejob / office, Handover, Onsite with counts, grouped by job (required first, then oldest), 10 jobs per group then "Show all", search on free tasks. A task with open subtasks shows "Open job" instead of Done.
- **Clock-out cost-centre slider** (`cko-split-slider` in `public/js/supabase-client.js`): split the shift's hours across stages at clock-out, waterfall redistribution. Closed variations drop out of the list; do-and-charge variations can take time.
- **Who's clocked in:** "Clocked in now" card on Schedule and Team, "On this job now" with clock in/out/switch on a job's Summary (migration 147, `get_active_clock_ins`).
- **Schedule month view (21 Oct 2026, backlog item 28):** equal-width day columns, fixed cell height (120px, 80px on phone) with the chip list scrolling inside the cell and a fade at the bottom while more is below, a booking count next to the day number, one chip per job per day with the first names on it (leave stays per person; no-job blocks show Inspection, Site visit, Training, Admin or Other). Bookings only: a time entry never creates a booking, so a timesheet added later with no booking does not show on the schedule. `public/schedule.html` only, no migration.
- No overlapping entries; at least one cost centre per entry.
- **Unpaid break (owner, 24 Oct 2026):** one `time_entries` row per shift with `break_minutes` on it; paid hours = clock span minus the break, everywhere (Xero push, labour cost, stage actuals, itemised labour, invoiceable actuals, monthly net). The clock-out asks about the break only when the shift runs past 6 hours (default Yes, 30 minutes); a shorter shift skips the question. A clock-out in flight cannot be sent twice.
- Timesheet categories: Billable (Jobs), Quoting, Admin, Maintenance, TAFE, Training (migration 134). One-click TAFE day: one row, 8 paid hours as Training with a 30 minute unpaid break on the row.
- **Admin/Finance timesheet dashboard:** everyone's timesheets, editable, flags any day over 6 hours with no break.
- **LAHA:** a job over ~100 km from base can be flagged "LAHA approved"; clock-out asks about an overnight stay; confirmed nights push as a separate LAHA earnings line (once per day per project).
- **Xero Payroll push (live):** timesheets push on demand, split by the Work Type tracking category (not per job: Xero caps a category at 100 options). Ordinary, OT1, OT2 and Public Holiday bands each map to a **Jobs** and an **Office** earnings rate (migration 151). Public holidays pay base plus penalty (migration 152). Timesheets arrive in Xero as DRAFT and are approved there (owner, 26 Oct 2026). From 26 Oct 2026 Xero is the check for "already sent": before building anything the push reads each employee's timesheets in Xero (`GET payroll.xro/1.0/Timesheets`, by employee), un-marks `xero_pushed_at` on entries whose day is inside no live Xero timesheet (deleted there when a pay run was redone) and sends them again, frees the matching `public_holiday_pay_pushes` days, and never re-sends a day a live Xero timesheet (draft, approved or processed) still holds. The result lists what was re-sent and what Xero still holds. If Xero cannot be read for someone, their marks stay as they were. Xero keeps one timesheet per employee per period, so (26 Oct 2026, migration 20261126000000) a timesheet already there for the same dates (draft, approved, rejected) is updated with the whole period's hours (`POST Timesheets/{id}`, status DRAFT) instead of a second one being created, and Xero's total is read back and compared; one in a posted pay run is left alone with a message; one with different dates that overlaps blocks that person until it is deleted in Xero or the push uses its dates. A Xero "already exists" for a timesheet it does not list gets a plain message (show rejected timesheets in Xero, delete, push again).
- **Leave to Xero (26 Oct 2026, migration 20261126000000):** approved leave requests that fall in the pushed period go to Xero as leave applications (`POST LeaveApplications`: annual, sick, unpaid; "other" is listed for the office to handle by hand) in the same push. Xero works out the hours from the person's ordinary hours and splits them across pay periods itself; a request is sent whole the first time any period it touches is pushed. The Xero id and hours are kept on the request (`leave_requests.xero_leave_application_id`, `xero_pushed_at`, `xero_units`); one still in Xero is never sent twice, one deleted there is sent again. Leave types come from Settings > Xero Mapping (`company_settings.xero_annual_leave_type_id`, `xero_sick_leave_type_id`, `xero_unpaid_leave_type_id`; blank = matched by name from Xero's PayItems the first time and saved). Warnings: hours clocked on a leave day, a weekday public holiday inside the leave, a second approved request covering the same days (not sent), Xero returning 0 hours. Staff RLS split in the same migration: a person can add and change their own request only while it is pending and can never set its status, decider or Xero columns (the old "for all" policy let a person approve their own through the API). Dates are checked (2020 to 2100).
- **Leave card (26 Oct 2026):** Timesheets page, Admin and Finance: everyone's leave in one table (who, kind with sick in red, when, working days, status, decided by whom and when, Xero sent or "with the next push"), filters for status, kind and "last 60 days and ahead" or everything, Approve and Decline on the waiting ones. **Add leave for someone** (8 Nov 2026, item 60, migration 20261130020000): Admin and Finance pick a person, dates, kind and notes; "Mark approved now" (on by default) saves it approved and decided by them, otherwise it waits like a staff request. The Xero columns can never be set by hand. **Delete** on every row, any status, Admin and Finance only (staff still withdraw only their own waiting requests); leave already pushed to Xero stays in Xero Payroll and the confirm says to delete it there too. Staff: "My leave requests" shows each request's kind, dates, working days, who approved or declined it and when, and whether it is in Xero payroll.
- **Pay rates to Xero:** each employee's 4 contract rates (set in the app) push into their Xero pay template (`push-pay-rates-to-xero.js`, migration 150); Settings > Users & Roles flags anyone whose rates changed but were not pushed.
- **Link employees to Xero:** `link-employee-to-xero.js` links to the existing Xero employee record instead of creating one.
- Pay templates and payroll calendars stay in Xero. TFN, super and bank details are collected by Xero's own onboarding, never by the app.

- **The savings estimate (11 Nov 2026, backlog item 72b, no migration):** `public/js/solar-roi.js` (the maths and the page content, on the client's proposal and in the bill card's preview) and `public/js/solar-roi-staff.js` (the staff-only checks, the working and the plan finder's grouping; loaded by `project.html` only). **What the figures rest on:** the home is worked out once (`roiHome`) and shared by the estimate and the plan options. The **sun figure** (kWh a day from each kW of panels) is the year's average with cloudy days and normal losses already in it: the Clean Energy Council's guide figure for the site's STC zone, and within zone 3 a Queensland (4000 to 4999) or Northern Rivers (2460 to 2490) postcode on the site address takes Brisbane's 4.2 where the rest take Sydney's 3.9 (`roiSiteYield`, item 72c). ## Key principles

- Numbering is internal Postgres counters, independent of Xero.
- Run migrations before or with the deploy.
- Settings-driven values, not hardcoded.
- Credentials in `api_keys` (via `getIntegrationKey()`) or Netlify env vars, never in code.
- New tables: fast RLS (`(select auth.uid())`), one policy per action, index every FK.
- Sliders: no full re-render on drag; waterfall redistribution.
- Review before save for anything AI enters.
- Keep screens simple; small learning curve.
- "Admin can change it, the user can't" needs a BEFORE UPDATE trigger, not just RLS.
- Compress every image (`compressImage()`).
- Every build goes through the software factory (`docs/SOFTWARE_FACTORY.md`, 27 Oct 2026): own branch, code in the right place, proof with before and after screenshots, PR template, weekly cleanup. `npm run check` fails on new dead code and on a page over its weight budget.
